# M5 자동 플레이 시나리오 설계

`test-scenarios.json`은 단계별 입력·조작, 활성 시각, 기대 사건 ID 순서, 금지 결과와 공개 경계 확인 항목의 기계 판독용 원본이다. **아직 실행한 M5 자동 플레이 결과가 아니다.** `events.json`도 실행 계약이 아닌 초안이다.

## 시나리오 목록

| ID | 동선 | 핵심 확인 |
|---|---|---|
| S01 | 기본 동선·선택 회의·세 행동 | 작성 초안 확인 뒤에만 작업 생성, 비밀·선제공격 제한 유지 |
| S02 | 5초에 주유 먼저 | 장조 접견 불필요, T06 독립 도착, T07 중복 요청 취소 |
| S03 | 10초에 유비 타진 | 급보·접견 이전 명령 허용, 25초 전 출발 없음, T10 생략 |
| S04 | 노숙·회의 생략 | 수군 정비만으로 후속 반응, 노숙 출발·동맹 보고 없음 |
| S05 | 15분 동안 무결정 | T11·T12만 해당 조건에서 발생, 자동 패배·작업·소모 없음 |

## 하네스 실행 규칙 제안

1. 각 시나리오는 동일 fixture와 새 세션에서 시작한다. 현재 초기 군량·준비도·요청 상태는 엔진에서 읽고 시나리오가 변경하지 않는다. 대사 선택은 인물·태그별 순환 인덱스 0부터 시작한다.
2. `atActiveMs`는 절대 목표 시각이다. 현재 `FakeClock.advance` 한 번은 양수 60000ms 이하이므로 큰 간격은 나눈다. 0ms 단계에서는 0으로 advance하지 않는다. 같은 시각의 단계는 JSON 배열 순서를 따른다. S07의 재실행은 새 타임라인이며 마지막 단계 자체를 재귀 실행하지 않는다.
3. 실제 입력 중·AI 대기·확인 패널 등 보류 사유를 구별한다. ‘확인’은 반환된 초안 ID·버전을 써야 한다. 시나리오에 전략적 실행 확인이 있는 것은 게임 안의 시험 조작이며, 작업 수행 도중 사용자에게 확인창을 띄우라는 지시가 아니다.
4. `expectedEventOrder`는 열거한 ID들의 최초 발생 순서다. T13은 여러 실제 진행 기록을 가질 수 있어, 각 단계의 기대와 taskId·sourceEventId·수신자를 추가 검사한다. 목록만 부분 일치시키고 끝내지 않는다. 전체 로그에서 `forbidden` 결과, 중복 발생, 예상 밖 소모도 검사한다.
5. 고정 사건·작업 진행·대화 발언을 구분한다. 직접 호출은 T05/T07의 ‘접견 요청 도착’이 아니다. 공유는 별도 서버 행동이며 이 콘텐츠의 T 번호를 부여하지 않았다. M4 계약의 실제 기록과 연결한다.
6. 각 단계 전후로 공개 플레이어 뷰, 해당 인물의 지식 뷰, Provider 입력을 수집한다. PB01~PB06을 해당 시나리오의 `boundaryIds`대로 적용한다. 서버 내부값 비교는 테스트 전용 접근에서만 하고 공개 결과에 복제하지 않는다.
7. 실행·완료·취소·지식 증가를 검증할 때 대사 문자열만 보지 않는다. 서버 상태와 원인 이벤트를 확인하고, 화면의 표시가 그 결과에 맞는지 비교한다. T14도 실제 시작 이후 반응을 관찰해야 성립한다.

## 문장과 Provider의 현재 지원 수준

근거는 `docs/COMMANDS.md`, `server/mock-interpreter.ts`, `server/compound.ts`, `tests/fixtures/scripted-provider.ts`다. 단순 구형 `server/provider.ts`의 MockLLMProvider와 현재 명령용 MockCommandInterpreter를 혼동하지 않는다.

- **명령 지원:** 명시된 수군 정비, 조조 보류·따옴표 회신, 유비 타진 문장. 실제 파서에서 `command`이고 미해결 목록이 비어 있는지 추가 점검한다. 이 표시가 M5 사건이나 M4 대화까지 현재 구현되었다는 뜻은 아니다.
- **질문 분류만:** Mock이 `question`으로 분류할 뿐, 사료 근거나 작성 대사를 답하지 않는다. 유의미한 인물 답변은 **Provider 필요** 또는 M4 작성 대사 선택기의 명시적 연결이 필요하다.
- **Provider 필요:** 회의 요청 같은 현재 파서 미지원 문장. 미래 Provider가 의도를 제안하더라도 실제 호출·접견은 M4 서버 계약으로 검증해야 한다. Provider 하나를 붙이는 것으로 미구현 행동이 실행되지는 않는다.
- **ScriptedProvider:** 모든 문장에 대해 **Provider 필요**로 표기한다. 이 fixture는 자연어 판독기가 아니라 주입한 응답을 순서대로 반환하는 도구다. M3 명령은 현재 schema와 원문 검증을 만족하는 별도 응답 fixture를 작성하면 오프라인 재생할 수 있다. M4 대화·호출은 계약 확정 뒤 응답과 하네스 연결이 추가로 필요하다. 이 작업은 응답 fixture나 연결 구현을 만들지 않는다.
- **조작:** 문서 열기·공유·접견·확인·시계 전진은 UI/하네스 동작이며 문장 인식의 성공으로 세지 않는다. 현재 미구현 조작은 M4/M5 연결 전 **미검증**이다.

## 미검증 범위

정적 검사와 명령 파서 점검은 위 시나리오를 실제 게임에서 플레이한 증거가 아니다. M4 상태·API, M5 스케줄러, 브라우저 초점·입력 유지, 비밀 보고의 실제 표시·전달, 재미와 한국어 자연스러움은 통합 후 확인해야 한다. 역사 정확성은 `historical-notes.md`의 사람 검증 체크리스트를 따른다.
