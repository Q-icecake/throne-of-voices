# 오프닝 사건 설계 — 구현 아님

근거: `PROTOTYPE_SPEC.md` 6장(활성 시간·조건·자유·후속 반응), `SCENE_PLAN_v0.1.md` 10장(첫 15분의 목표 흐름). 시간과 세부 조건은 이 작업의 재구성 제안이며 확정된 서버 계약이 아니다. M4가 확정되기 전 `shared/contracts.ts` 변경을 제안하지 않는다.

`events.json`은 아래 목록을 기계적으로 참조하기 위한 **데이터 모양 초안**이다. `trigger`, `prerequisites`, `onceScope` 등의 문자열을 실행식으로 평가하지 않는다. M5 구현자는 확정된 서버 상태에서 명시적 판정 코드를 작성해야 한다.

## 시간·정렬·중복 방지

- 0ms는 로딩과 입력 준비가 끝난 때다. 실제 벽시간·역사 날짜와 다르다. 입력 중·음성 처리·AI 대기·명령 확인·명시적 일시정지에는 사건용 활성 시간이 흐르지 않는다는 설계 원칙을 보존한다. 현재 `FakeClock`의 사유와 M4 이후 실제 UI 연결은 통합 때 확인한다.
- 도착 시각은 문서의 관측 시각과 다르다. `observedAt.activeMs: null`은 시각 미상이며 0으로 바꾸지 않는다. 이미 발송한 보고는 담당자의 이후 정비·파견과 독립적으로 도착한다.
- 고정 시각은 가장 이른 자격 시각이다. 전제 미충족이면 보류하고, 취소 조건을 먼저 검사한다. 시간 전진은 중간 임계값을 순서대로 처리한다. 같은 시각의 콘텐츠 사건은 T 번호 순서, 그 후 해당 시각의 엔진 진행 기록을 안정된 원인 ID 순서로 투영한다. 이는 재현 시험을 위한 제안이며 현재 엔진의 새 규칙이라고 주장하지 않는다.
- 사용자 입력은 시계를 목표 시각까지 처리한 뒤 실행한다. 단, T11 취소의 경우 실제 회신 **완료**가 먼저 기록되어 있어야 한다. 회신 초안이나 확인만으로 answered를 추정하지 않는다.
- `T13`은 종류 ID다. 실제 인스턴스는 `(T13, sourceEventId, 수신자)`로 구별한다. 스케줄러가 작업 비용·진행·보고를 다시 실행하면 안 된다. 엔진 보고를 재사용하거나 연결하는 방식으로 중복 노출과 중복 소모를 막는다.
- `T14`는 플레이어가 시작 이후 후속 반응을 관찰한 지표다. 예: 정비는 착수 후 완료 보고, 타진은 명 전달 후 출발 보고, 회신은 전달 후 처리 결과. 시작 기록 하나만으로 지표를 달성하지 않는다. 자동 종료도 하지 않는다.

## 도착·열람·공유·발언

문서의 `readers`와 지식의 `eligibleReaders`는 접근 가능 상한이다. 도착 이벤트가 실제 수신자를 기록해야 지식을 얻는다. T01·T02·T03·T04·T06의 플레이어 측 수신자는 손권(`player`)과 장굉이다. T04에는 장조의 급보 별도 수신과 건의문 작성이라는 명시적 선행 기록이 필요하다. 이것이 같은 방에 있거나 플레이어가 문서를 연 효과가 되어서는 안 된다. 주유는 자기 작성 보고를 개시 때부터 알고 있다.

작성자가 아닌 인물은 승인된 공유·전달 이전에 해당 지식이 없다. 노숙에게 급보를 공유할 수 있지만, 장조 건의문의 허용 목록에는 노숙이 없으므로 이번 고정 목록에서는 공유를 거부한다. M4가 다른 권한 정책을 확정했다면 통합자가 데이터 매핑을 검토할 사항이며, 이 초안이 새 계약을 강제하지 않는다.

사건의 `dialogueTags`는 후보 검색 힌트다. **인물 + 태그 + 필요한 모든 지식 + 현재 접견/전달 가능 상태**를 동시에 검사한다. 태그가 같은 다른 인물의 대사를 고르지 않는다. 문서 `documentIds`도 관련 링크일 뿐 자동 공유 목록이 아니다. 연기 반응은 그 결정이 해당 인물에게 실제 전달됐을 때만 쓴다. 무시한 요청에는 수신 확인이나 반응을 지어내지 않는다.

T11의 ‘재촉 도착’은 사건 알림이다. 장굉의 정적 after-document 대사는 서신 설명에만 쓰며 재촉이나 회신 완료를 증명하지 않는다. T12는 실제 미결 항목만 서버에서 추려 수신자 권한에 맞게 표시한다. T13의 완료·출발 문구는 이 정적 대사 풀에서 만들지 않는다.

## 현재 기준과 M5에 넘길 차이

현재 `server/world.ts`에는 `cao-cao-envoy` 요청이 0ms에 이미 pending으로 있다. 따라서 이 초안의 T03은 새 요청 생성이 아니라 같은 요청의 서신 도착이다. 40000ms 이전 회신도 허용하고, 나중에 서신이 도착했다고 응답 상태를 되돌리지 않는다. 통합 시 요청 생성 시각을 바꾼다면 T11 하한과 S06·S10의 기대 시각을 함께 조정해야 한다.

현재 `server/rules.ts`의 명령 시간은 별도 기준이다. 정비는 전달 10000ms + 작업 30000ms, 타진은 전달 5000ms + 준비 10000ms + 이동 15000ms + 회신 대기 30000ms다. 실제 값은 엔진에서 읽고 콘텐츠의 예정 시각으로 덮어쓰지 않는다. 기존 비용·준비도는 역사적 수치가 아니다.

M5 범용 사건 스케줄러, M4 대화 연결, 계획·도움 이력의 판정, 동적 지식 발급은 이 작업에서 구현하지 않았다. 미래 사건 대기열·전체 지식 목록·모든 문서 본문을 브라우저나 Provider에 그대로 보내지 않는다. 읽기 가능한 현재 뷰와 현재 인물의 지식만 허용 필드로 투영한다.
