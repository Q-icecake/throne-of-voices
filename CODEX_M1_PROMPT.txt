# Throne of Voices — 궁정 중심 화면 보강 + M1 구현

이번 작업은 계획만 다시 쓰는 것이 아니라, 기존 M0를 보존하면서 M1을 실제로 구현하고 검증하는 작업입니다. 전체 15분 게임을 한 번에 만들지는 마세요. 응답·게임 UI·사용자 실행 안내는 한국어로 작성하세요.

## 1. 먼저 읽고 확인할 것

프로젝트의 기존 지침이 있다면 AGENTS.md를 먼저 확인하고, 다음을 읽으세요.

- PROTOTYPE_SPEC.md
- DEVELOPMENT_PLAN.md
- VISUAL_DIRECTION.md
- SCENE_PLAN_v0.1.md
- references/REFERENCE_NOTES.md
- 기존 README, 실행 스크립트, package.json, 테스트, 실제 M0 코드

references/ck3-court-close.png와 references/ck3-court-wide.png를 직접 보고 공간·인물·UI의 관계를 파악하세요. references/m0-current.png는 기존 시험 화면 참고입니다. 이름만 보고 원하는 디자인을 추측하지 마세요.

현재 폴더와 Git 상태를 확인하세요. 원래 M0는 테스트 17개 통과라는 완료 보고가 있었지만, 그 보고만으로 지금 상태를 검증했다고 하지 마세요. 실제 테스트·타입 검사·빌드를 다시 실행하여 기준 상태를 기록하세요. 실행 불가 항목은 이유를 구분하세요.

이 문서 패키지에는 M0 소스 코드나 완성된 궁정/인물 아트가 없습니다. 현재 프로젝트의 실제 소스가 없으면 새 M0를 임의로 재생성하지 말고 그 사실을 알리세요.

## 2. 문서 우선순위와 이번 변경

게임 철학과 상태·정보 규칙은 PROTOTYPE_SPEC.md를 유지합니다.
기술 구조와 M0~M6 단계 번호는 DEVELOPMENT_PLAN.md를 따릅니다.
화면 표현은 VISUAL_DIRECTION.md, 이번 구현 범위와 검증은 SCENE_PLAN_v0.1.md로 보완합니다.

사용자의 최신 방향은 CK3 참고처럼 하나의 궁정 공간에서 문서·지도·접견·명령을 다루는 것입니다. 따라서 기존 ‘지도 카드 중심 페이지’를 ‘궁정 기본 + 즉시 펼치는 지도·문서’ 구조로 바꾸는 것은 이번에 승인된 표현 변경입니다. 지도는 여전히 핵심 도구이며 접근을 없애거나 장식으로 만들면 안 됩니다.

기존 두 설계 파일을 전체 재작성하지 마세요. 이번 시각 보완과 작업 상태는 DEV_LOG.md 또는 기존 작업 기록에 남기세요. 그 외 핵심 설계와 충돌하면 변경 범위를 먼저 설명하세요.

## 3. Game Studio 사용

설치된 Game Studio에 접근 가능하면 다음 관련 Skill을 읽고 적용하세요.
- game-ui-frontend: 공간 중심 UI, 정보 계층, 읽기 쉬운 한국어 문서와 입력
- web-game-foundations: 시뮬레이션과 화면의 분리
- game-playtest: 실제 브라우저 조작·해상도·스크린샷 검증

플러그인의 일반 기본값을 이유로 기존 기술을 Phaser/Three.js/React/Unity로 바꾸지 마세요. 현재 TypeScript + Vite + HTML/CSS + SVG + 로컬 Node.js 서버를 유지합니다. Skill에 접근할 수 없으면 사용했다고 주장하지 말고 제공된 문서로 진행하세요.

## 4. 이번 목표와 제외 범위

목표:
궁정 중심 화면에서 시험 문서를 보고 장굉에게 수군 정비 지시를 입력한 뒤, 초안 확인 → 실제 작업 → 시간 진행 → 자원/준비 상태 변화 → 관련 보고를 확인할 수 있게 만드세요.

M1에서 실제로 연결할 화면:
- S0 궁정 기본
- S1 시험 문서/현황/처리 기록
- S2 장굉 한 명의 Mock 대화·명령 입력
- S4 시험용 지도 열기·닫기
- S5 명령 초안과 진행 상태

S3 다인 회의는 설계만 유지하고 실제로 구현하지 마세요. 4명의 자유 대화, 전체 오프닝 사건, 자동 25초 형주 급보, 조조·유비 외교 명령, 정찰, 음성 입력, LLM API 연결, 본격 전투는 이번 범위 밖입니다.

## 5. 구현 순서

A. 기존 기반 확인
기존 테스트·실행 방식을 파악하고 필요한 범위만 수정하세요. 사용자 변경을 덮거나 폴더를 재생성하지 마세요. 기존 엔진의 상태·가짜 시계·공개/비공개 분리·초기화·로그 구조를 재사용하세요.

B. 공간 중심 UI
전체 뷰포트가 정무 공간으로 읽히도록 구성하세요. 후경의 주군 자리, 중경의 장굉/접견 위치, 전경의 책상 흔적과 자료를 계층화하세요. 기본 화면 중앙을 넓게 비워 두고 입력은 하단, 작은 상태·도구는 가장자리에 두세요.

문서와 지도는 같은 공간 위에 필요할 때 펼치세요. 기존 대시보드 뒤에 큰 배경만 붙이는 것으로 끝내지 마세요. 페이지 전체를 아래로 스크롤하지 않고 주요 입력과 확인을 사용할 수 있어야 합니다. 긴 문서·기록은 내부에서만 스크롤하세요.

큰 제목, 긴 시험 설명, 가짜 시계 조작, JSON 로그는 기본 화면에서 접고 개발 도구로 이동하세요. 단, Mock/시험 모드라는 사실은 작은 표시로 계속 알리세요. 개발 도구를 없애거나 숨겨진 서버 상태를 브라우저로 새로 노출하지 마세요.

완성 아트가 없으면 자체 제작한 단순 원근 SVG·레이어·임시 인물 표현으로 시작하세요. 그 경우 구조 시안과 최종 미술 완성을 구분해 보고하세요. 참고 CK3 스크린샷을 배경으로 복사하거나 게임 배포 자산으로 사용하지 마세요. 유료 이미지 생성이나 외부 자산 구매는 하지 마세요.

C. M1 한 명령의 연결
‘주유에게 수군을 정비하라고 전해. 먼저 공격하지는 마.’를 시험할 수 있게 하세요.

명시적인 Mock Provider로 입력/질문/지원 명령 사례를 구분하되 일반 자연어 해석을 완성했다고 하지 마세요. 미지원 표현은 조용히 정비로 바꾸지 말고 입력 원문과 이유를 남기세요. 기본적인 질문과 가정은 실행하지 않아야 합니다.

서버가 명령 초안의 ID·버전·행동·대상·담당자·금지 조건을 관리하고 검증하게 하세요. 검토 화면에서 확인·수정·초안 취소를 제공하세요. 패널을 닫는 것만으로 확인 또는 취소하지 마세요.

확인 시 최신 상태 재검사, 같은 초안의 중복 확인 방지, 확인 전 비용/상태 변경 없음, 수정·취소된 초안의 실행 방지를 구현하세요. 중복 클릭 방지를 버튼 비활성화에만 의존하지 마세요.

작업 등록·전달·수행·완료를 필요한 범위에서 구분하세요. 비용 소모 시점을 작은 테스트 규칙으로 명시하고, 시간을 보냈을 때 준비 상태/자원 변화와 보고가 실제로 일치하게 하세요. 대사나 애니메이션 자체가 실행의 증거가 되어서는 안 됩니다.

‘먼저 공격하지 마’ 조건을 작업과 보고에 유지하세요. 실제 공격 시스템은 구현하지 않습니다. 이 제한을 검증하기 위해 M1의 범위를 전투로 확장하지 마세요.

D. 통합 검증
화면 전환 중 입력·초안·작업을 보존하고, 렌더링/패널 열기/창 크기 변경이 작업을 중복 실행하지 않는지 검사하세요. 기존 M0 시험과 SCENE_PLAN의 M1 시험을 실제 수행하세요.

## 6. 안전·범위·사용성 규칙

- 실제 Gemini/OpenAI/ASR API를 호출하거나 API 키를 요구하지 마세요.
- 기존 문서의 모델명·요금은 이번에 확정하거나 구현하지 마세요. 실제 모델 접근 확인은 M2의 별도 작업입니다.
- 불필요한 프레임워크·데이터베이스·계정·배포 기능을 추가하지 마세요.
- 필요한 개발 의존성만 설치하며 가능한 기존 테스트 도구를 재사용하세요.
- 승인 없는 원격 push, 공개 배포, 프로젝트 자료의 외부 업로드, 유료 작업을 하지 마세요.
- 사용자 파일 삭제, 강제 reset/checkout, 관련 없는 변경 덮어쓰기를 하지 마세요.
- Git 변경과 기존 작업을 구분하세요. 커밋을 자동으로 만들 필요는 없습니다.
- 역사 내용은 기존 시험 자료를 사용하고 임시 고증·수치를 사실처럼 추가하지 마세요.
- 문서/지도/인물 초점을 바꾸는 UI 상태와 서버의 세계 상태를 분리하세요.
- 한국어 조합 중 Enter 오발송을 막고 현재 전송 방식을 일관되게 유지하세요.
- 문서 열기·닫기·확인·수정·일시정지는 조작 버튼으로 제공해도 됩니다. 전략을 항복/항전/동맹 정답 버튼으로 대체하지 마세요.
- 작동하지 않는 마이크나 회의 기능을 사용 가능한 것처럼 보여주지 마세요.
- 사소한 배치·여백은 문서 기본값으로 진행하고 결과에 적으세요. 구조 변경·유료 작업·중요 충돌만 질문하세요.

## 7. 실제 검증과 완료 증거

현재 스크립트에 맞게 테스트·타입 검사·빌드를 실행하세요. README에 이미 run.ps1 방식이 있다면 유지하는 것을 우선하세요.

가능한 브라우저 도구로 실제 페이지를 열고 다음 화면을 확인하세요.
1. 기본 궁정
2. 문서 검토
3. 지도 브리핑
4. 명령 확인 전
5. 확인 후 작업 및 보고

1920×1080과 1366×768을 확인하세요. 작은 해상도에서 입력·확인·닫기가 화면 밖으로 나가거나 문서 뒤에 가려지면 수정하세요. 스크린샷은 프로젝트의 일관된 검증 폴더에 저장하고 기본 화면/문서/명령 상태를 비교하세요. DOM 존재 여부만으로 시각 검증을 대체하지 마세요.

최소 기능 검증:
- 확인 전 자원·준비도·작업 불변
- 두 번 확인해도 작업과 비용은 한 번
- 수정/취소한 초안 미실행
- 금지 조건 유지
- 오래된 초안 재검사
- 가짜 시계를 진행한 실제 상태 변화와 보고의 일치
- 같은 초기 상태·입력·시계로 재현
- 패널 전환·반복 열기 후 입력·초안 보존
- 공개 스냅샷·브라우저 응답에 숨겨진 정보 없음

브라우저 실행이나 실제 Windows 한국어 IME를 검증하지 못하면 그 부분을 미검증으로 남기세요. 도구가 없어 확인하지 않은 결과를 성공이라고 하지 마세요.

최종 보고:
- 주요 변경 파일과 사용자에게 보이는 변화
- M0에서 보존한 기능

이 작업은 UI 보강을 포함한 M1 한 단계입니다. 실제 AI 연결이나 전체 오프닝으로 확장하지 말고 M1의 완료/남은 문제를 보고한 뒤 멈추세요.
